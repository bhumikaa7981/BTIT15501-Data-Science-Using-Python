Foundations of Pandas

The two building blocks every Pandas program starts with — and the six commands that let you "meet" any new dataset in under a minute.

Series & DataFrame

Pandas' two core objects — a labelled column, and a labelled table

💡 Why this exists

A plain Python list only knows position — item 0, item 1... A Series is a list that also knows names (an index), so you can ask for "Banana" instead of "item 1". A DataFrame is just several Series glued side-by-side into a full table. Every row and column carries a label — that's the whole magic of Pandas in one sentence.

🌍 Real-world picture

Open Excel in your head. One column of numbers labelled by row — that's a Series. The entire sheet, Name column + Marks column + Grade column together — that's a DataFrame. You've been using these ideas for years without a Python name for them.

🧠 Syntax Pattern
pd.Series([10, 20, 30])
pd.DataFrame({"name": [...], "marks": [...]})

Program 1 — Creating a Series

1 / 3 
import pandas as pd

marks = pd.Series([45, 67, 89, 32])
print(marks)
▶ Output
0    45
1    67
2    89
3    32
dtype: int64
Why: Pandas silently generates index labels 0,1,2,3 next to every value — you never asked for them, but you get them for free.

Program 2 — Series with a custom index

2 / 3 
fruits = pd.Series(
    [120, 90, 75],
    index=["Apple", "Banana", "Mango"]
)
print(fruits["Banana"])
▶ Output
90
Why: A custom index lets you fetch a value by a meaningful name instead of remembering "it was the 2nd item".

Values [120, 90, 75] are paired one-to-one with labels ["Apple","Banana","Mango"].

Not position 1 — the actual text label. It scans the index column for a match.

Program 3 — Creating a DataFrame

3 / 3 
data = {"Name": ["Riya","Aman","Zoya"],
        "Marks": [88, 72, 95]}
df = pd.DataFrame(data)
print(df)
▶ Output
   Name  Marks
0  Riya     88
1  Aman     72
2  Zoya     95
Why: A dictionary of lists becomes a full table — each dictionary key becomes a column name, each list becomes that column's values.
🐼 Witty takeaway: Series = one Excel column with name-tags on every row. DataFrame = the whole sheet. Master this pair, and every function from here on is just "something you do to a Series or a DataFrame."

Exploring a DataFrame

head(), tail(), info(), describe(), shape, columns, dtypes

💡 Why this exists

You would never build a formula on an Excel sheet you haven't scrolled through first. These six commands are your "scroll through" — a 30-second health check that tells you the size, the column names, the data types, and whether anything's obviously broken, before you calculate a single thing.

🌍 Real-world picture

Before analysing a new spreadsheet, you skim the top rows and check for weird or missing values. head() and info() do exactly that, in one line each — no more scrolling for ten minutes.

🧠 Syntax Pattern
df.head(n)          df.tail(n)
df.info()           df.describe()
df.shape   df.columns   df.dtypes

Program 1 — Previewing rows with head()

1 / 3
df = pd.read_csv("students.csv")
print(df.head(3))  # default is 5 rows
▶ Output
rollnameagecity
1aaa33a
2sss44s
3ddd22d
Why: head(3) previews just the first 3 rows out of however many exist — a lifesaver on files with 50,000 rows.

Program 2 — Checking size & column names

2 / 3
print(df.shape)
print(df.columns.tolist())
▶ Output
(50, 4)
['Name', 'Marks', 'Branch', 'City']
Why: shape = (rows, columns) at a glance; columns.tolist() lists every column name — handy when a dataset has 40 columns and you can't remember one.

Program 3 — The full health check: info() + describe()

3 / 3
print(df.info())
print(df.describe())
▶ Output
column dtypes + non-null counts,
then a mean/std/min/max table
Why: info() flags missing data early; describe() gives instant statistics for every numeric column — no formulas needed.

Getting Data In & Out

Loading real files into Python, and saving your cleaned results back out — the very first and very last line of almost every Pandas program.

📥

Import & Export — Reading Data

How your real project data gets into Python

💡 Why this exists

Nobody types their dataset by hand. Someone hands you a .csv or a .xlsx file, and you need it as a working DataFrame in one line — not fifty. read_csv() and read_excel() are that one line.

🌍 Real-world picture

Every real project starts with loading a sales report or an attendance sheet. This is always the very first working line of code you write.

🧠 Syntax Pattern
pd.read_csv("file.csv")
pd.read_excel("file.xlsx", sheet_name="Sheet1")

Program 1 — Reading a CSV file

1 / 3
df = pd.read_csv("students.csv")
print(df.shape)
▶ Output
(50, 4)
Why: Checking .shape right after loading instantly confirms the file actually came in correctly.

Program 2 — Reading a specific Excel sheet

2 / 3
df2 = pd.read_excel(
    "marks.xlsx", sheet_name="Sheet1"
)
# no sheet_name? defaults to Sheet1
print(df2.columns.tolist())
▶ Output
['Name', 'Marks', 'Grade']
Why: sheet_name picks exactly which sheet to load out of a multi-sheet workbook.

Program 3 — Loading only the columns you need

3 / 3
sales = pd.read_csv(
    "sales.csv", usecols=["Date","Amount"]
)
print(sales.head(2))
▶ Output
DateAmount
01-Jan1200
02-Jan950
Why: usecols loads just the columns you actually need — much faster on huge files with 40+ columns.
🔎 The "Where's my file?" trace — 3 ways to point to a CSV
1
Same folder as your script
Python looks in the current folder first — simplest option.
df = pd.read_csv("student.csv")
2
A different folder — use the full path
Prefix with r so Windows-style backslashes aren't misread as escape codes (\n would otherwise become a newline!).
df = pd.read_csv(
  r"C:\Users\Bhumika\Documents\Data\student.csv"
)
3
Working in Google Colab
Upload the file into the session first, then read it exactly like a local file.
from google.colab import files
uploaded = files.upload()
df = pd.read_csv("student.csv")
📎 Witty takeaway: 90% of "FileNotFoundError" panic is just a path problem. Same folder → plain name. Different folder → full path with r. Colab → upload first.

Import & Export — Saving Data

How your cleaned results get back out of Python

💡 Why this exists

Cleaning data inside Python is pointless if nobody else can use the result. to_csv() / to_excel() hand your work back as an ordinary file anyone can open — in Excel, Google Sheets, or another script.

🌍 Real-world picture

After removing duplicate customer records, you export the cleaned list so it can be emailed to the sales team as a proper, ready-to-open spreadsheet.

🧠 Syntax Pattern
df.to_csv("out.csv", index=False)
df.to_excel("out.xlsx", sheet_name="Report", index=False)

Program 1 — Saving a cleaned CSV

1 / 3
df.to_csv("clean_students.csv", index=False)
print("Saved!")
▶ Output
Saved!
(file written to disk)
Why: index=False keeps the output file clean — no stray, meaningless "0,1,2..." column tacked onto the front.

Program 2 — Exporting a filtered subset

2 / 3
toppers = df[df["Marks"] > 85]
toppers.to_csv("toppers.csv", index=False)
▶ Output
file "toppers.csv" created,
containing only high scorers
Why: You can export any filtered slice of your data, not just the whole table.
🔎 Trace — how "only toppers" gets saved

Program 3 — Saving to Excel

3 / 3
df.to_excel(
    "report.xlsx", sheet_name="FinalReport", index=False

💾 Witty takeaway: Reading gets data in; saving gets your work back out. Always set index=False unless you specifically want that extra numbering column in the file.

Selecting & Cleaning Data

Picking exact cells like a surgeon, then handling the gaps that real-world data always, always has.

🎯

Selecting Data — loc, iloc, at, iat

Picking exact rows, columns and cells out of a table

💡 Why this exists

loc selects by LABEL (the name); iloc selects by POSITION (the number), exactly like list slicing. at/iat are their turbo-charged cousins, built for grabbing just one single cell fast.

🌍 Real-world picture

"Give me Aman's marks" is a label lookup — loc. "Give me the 3rd row" is a position lookup — iloc. Like referencing an Excel cell by name (B5) versus counting rows down manually.

🧠 Syntax Pattern
df.loc[row_label, col_label]
df.iloc[row_position, col_position]
df.at[row_label, col_label]     df.iat[row_pos, col_pos]

Our running example table for this whole topic:

IndexNameMarksCity
S1Alice85Surat
S2Bob90Mumbai
S3Charlie78Delhi
🔎 loc vs. iloc — same answer, two totally different routes
🏷️ df.loc["S2", "Marks"] — by LABEL
IndexNameMarksCity
S1Alice85Surat
S2Bob90Mumbai
S3Charlie78Delhi
Row label = "S2", Column label = "Marks" → 90
🔢 df.iloc[1, 1] — by POSITION
#0Name (0)Marks (1)City (2)
row 0Alice85Surat
row 1Bob90Mumbai
row 2Charlie78Delhi
Row position 1, column position 1 (counting from 0) → 90
⚡ Same cell, same value — loc got there by reading names, iloc got there by counting. Big difference: with loc, a range like "S1":"S2" includes the last label; with iloc, 0:2 excludes position 2 — just like normal Python slicing.

Program 1 — Selecting by label with loc

1 / 3
print(df.loc[2, "Name"])
▶ Output
'Zoya'
Why: loc[2, "Name"] reads the row labelled 2, in the column labelled "Name".

Program 2 — Selecting by position with iloc

2 / 3
print(df.iloc[0:3, 0:2])
▶ Output
first 3 rows,
first 2 columns
Why: iloc uses pure position — exactly like Python list slicing, end excluded.

Program 3 — Reading/updating one cell with at

3 / 3
df.at[1, "Marks"] = 100
print(df.at[1, "Marks"])
▶ Output
100
Why: at[] (and its position-based twin iat[]) is the fastest way to read or update a single cell in a huge table.
🎯 Witty takeaway: Name in mind → loc. Number in mind → iloc. Just one cell, need for speed → at/iat.

Handling Missing Values — Detecting

Real-world data is messy. Finding the gaps comes before fixing them.

💡 Why this exists

isnull() flags every missing (NaN) cell as True; notnull() is the exact opposite. Chain .sum() straight after to turn a giant grid of True/False into a simple per-column count.

🌍 Real-world picture

Before analysing an attendance sheet, you must first know exactly which student rows have a missing "Marks" entry — this is that check, automated.

🧠 Syntax Pattern
df.isnull()      df.isna()
df.notnull()
df.isnull().sum()

Our messy starting table:

NameMarksCity
0Alice85Surat
1BobNaNMumbai
2None78None
3David92Delhi
🔎 Nested trace — df.isnull().sum() step by step
1
Step 1 — df.isnull() scans every cell
Each cell becomes True (missing) or False (present).
NameMarksCity
0FalseFalseFalse
1FalseTrueFalse
2TrueFalseTrue
3FalseFalseFalse
2
Step 2 — .sum() adds each column top-to-bottom
Pandas treats True as 1 and False as 0, then totals every column.
NameMarksCity
111
Final printed result: Name 1, Marks 1, City 1 — one gap in each column.

Program 1 — Counting missing values per column

1 / 3
print(df.isnull().sum())
▶ Output
Name      0
Marks     3
Branch    1
dtype: int64
Why: Shows the missing-value count for every column at a single glance.

Program 2 — Viewing only the problem rows

2 / 3
print(df[df["Marks"].isnull()])
▶ Output
only the rows where
Marks is missing
Why: Combining isnull() with filtering shows you the exact rows causing trouble — not just a count.

Program 3 — Counting valid (non-missing) entries

3 / 3
print(df.notnull().sum())
▶ Output
Name      50
Marks     47
Branch    49
dtype: int64
Why: notnull() is the mirror image of isnull() — confirms exactly how many complete entries exist.
🔍 Witty takeaway: isnull() and isna() are identical twins — literally the same function under two names. Detect first, decide later (fill it, or drop it — next up!).
🩹

Handling Missing Values — Filling

Replacing gaps with a sensible value instead of leaving them blank

💡 Why this exists

fillna() can patch gaps with a fixed value, the column's mean/median, or simply the previous row's value (forward-fill). Picking the right strategy matters — fill wrong, and you quietly bias every calculation that follows.

🌍 Real-world picture

If 3 students didn't report their marks, filling with the class average is far fairer than leaving the cell blank or forcing it to zero (which would tank the whole class's average).

🧠 Syntax Pattern
df.fillna(value)
df["col"].fillna(df["col"].mean())
df.fillna(method="ffill")
🔎 Nested trace — df["Marks"].fillna(df["Marks"].mean())
1
Start: Marks column has gaps
NameMarks
Alice85
BobNaN
Charlie78
DavidNaN
2
Inner call first: df["Marks"].mean()
Pandas ignores the NaNs and averages what's actually there: (85 + 78) ÷ 2 = 81.5
3
Outer call: every NaN becomes 81.5
NameMarks
Alice85
Bob81.5
Charlie78
David81.5
Filling with the mean preserves the overall distribution — filling with 0 would have wrecked it.

Program 1 — Filling with the column mean

1 / 3
df["Marks"] = df["Marks"].fillna(
    df["Marks"].mean()
)
print(df["Marks"].isnull().sum())
▶ Output
0
Why: NaNs get replaced by the column average, so zero missing values remain afterward.

Program 2 — Filling text columns with a label

2 / 3
df["Branch"] = df["Branch"].fillna("Unknown")
print(df["Branch"].unique())
▶ Output
array(['IT', 'CE', 'Unknown'], dtype=object)
Why: Text columns usually get a placeholder label instead of a number — "Unknown" is honest about the gap.

Program 3 — Forward-filling from the previous row

3 / 3
df_filled = df.fillna(method="ffill")
print(df_filled.head())
▶ Output
DayTemp (before)Temp (ffill)
Mon3030
TueNaN30
WedNaN30
Thu3232
Why: Forward-fill copies the last known value downward — ideal for time-series like a daily temperature or attendance log.
🩹 Witty takeaway: Number gap → usually mean. Text gap → a clear label like "Unknown". Data over time → forward-fill. Choose on purpose, never by accident.
🗑️

Handling Missing Values — Dropping

Sometimes the safest option is to remove incomplete data entirely

💡 Why this exists

dropna() deletes rows (or columns) that contain gaps, instead of guessing a replacement value. axis=0 (default) drops rows; axis=1 drops columns; subset=[...] only checks the columns you name.

🌍 Real-world picture

If a student's entire record — both Name and Marks — is missing, it's safer to drop that row than to guess and fill it with a fake identity.

🧠 Syntax Pattern
df.dropna()
df.dropna(axis=1)
df.dropna(subset=["col"])

Our starting table:

NameMarksCity
0Alice85Surat
1BobNaNMumbai
2Charlie78NaN
3NaN90Delhi
🔎 Three ways dropna() cuts the exact same table
A
df.dropna() — any gap, row gone
NameMarksCity
0Alice85Surat
1BobNaNMumbai
2Charlie78NaN
3NaN90Delhi
Only row 0 survives — every other row had at least one gap somewhere.
B
df.dropna(axis=1) — any gap, whole column gone
Every single column here has at least one NaN somewhere — so axis=1 wipes out all three, leaving an empty DataFrame. Ouch. This is why axis=1 is used carefully, usually only on wide, mostly-clean tables.
C
df.dropna(subset=["Marks"]) — only check ONE column
NameMarksCity
0Alice85Surat
1BobNaNMumbai
2Charlie78NaN (ignored)
3NaN (ignored)90Delhi
Only row 1 is removed — because only "Marks" was checked. Charlie's missing City and the missing Name in row 3 are ignored entirely.

Program 1 — Dropping all incomplete rows

1 / 3
df_clean = df.dropna()
print(df_clean.shape)
▶ Output
(46, 4)
Why: Any row with even one missing value is removed — the row count naturally shrinks from 50 to 46.

Program 2 — Dropping based on one column only

2 / 3
df_clean2 = df.dropna(subset=["Marks"])
print(df_clean2.shape)
▶ Output
(47, 4)
Why: Only rows missing "Marks" specifically get dropped — gaps in other columns are ignored, so fewer rows are lost.

Program 3 — Dropping incomplete columns

3 / 3
df_clean3 = df.dropna(axis=1)
print(df_clean3.columns.tolist())
▶ Output
['Name', 'Branch']
Why: axis=1 removes entire columns that contain even a single missing value — here, "Marks" and "City" got wiped, but "Name" and "Branch" happened to be complete.
🗑️ Witty takeaway: dropna() is the nuclear option — powerful, but it deletes data forever. Always check .shape before and after so you know exactly how much you just threw away.
